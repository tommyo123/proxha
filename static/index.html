Resource groups

Reusable guest and host groups for placement rules.

Guest groups can contain VMs and containers. Host groups contain hosts only. Resources may belong to several groups. Groups define membership; configure affinity and host-binding rules below.

Placement rules

Keep guest groups together, separate them, or bind them to host groups.

Must rules are enforced before migration and repaired every 15 seconds, independently of continuous balancing. Must together-groups share one destination and reserve capacity as a unit. Should rules are weighted preferences; their benefit competes with migration cost and load. They never force immediate repairs or block manual moves. Enforced rules permit recorded exceptions during maintenance or when compatible hosts are unavailable, then repair placement when possible. Report-only rules show violations without moving guests. Backup, storage and capacity checks always apply. Configure repair and group concurrency in DRS Settings.

Migration domains

Create separate groups for compatible hosts. Automatic balancing runs independently within each group.

Only hosts in the same enabled group may participate in automatic live migration. Each host belongs to one group. Group membership declares compatibility you have verified; it does not detect CPU compatibility.
These are local ProxHA policies. Proxmox HA rules and manual migrations are managed separately.

    DRS and maintenance settings

    Enabled schedules and continuous balancing migrate automatically. Run now starts a manual queue. Scheduled runs take priority over continuous balancing. Evaluate now remains a preview.

    VM balancing

    Run now live-migrates VMs only, one guest or together-group at a time, even when the schedule is off. Each completed move is followed by a 60-second settling period and a fresh assessment. Stop queue prevents the next move; the current migration finishes.

    VM automation mode

    Controls VM scheduling and continuous VM balancing. The VM + LXC schedule is configured independently below. Off pauses all planning. Continuous balancing switches on or off immediately; Save settings applies the rest. Continuous aggressiveness from 1 to 5 controls how readily guests move.

    Balloon recovery

    Target admission leaves two percentage points below the host ballooning target. Existing cooldowns, migration domains, local disk exclusions and stickiness still apply. The manual recovery button remains available when this priority is disabled.

    Continuous balancing

    The enable checkbox saves immediately; aggressiveness saves when you release the slider. Other settings use Save settings.

    Higher levels accept smaller sustained improvements and shorten the delay between moves. History penalties, an increasing guest cooldown and six-hour return protection reduce repeated moves. Shared storage, compatibility, stickiness 10 and target capacity still apply. Unchecking Enable continuous balancing prevents new moves and lets submitted migrations finish. Constraints and recoverable errors are checked again automatically.

    Balancing effort

    Lower scores allow smaller improvements. Scheduled balancing uses these settings independently of continuous aggressiveness. Thorough gives allocation balance and balloon recovery more priority than migration cost. Run now keeps reassessing and moving one guest or together-group at a time, without a fixed migration count limit. Scheduled runs ignore migration-failure penalties and the continuous hourly limit, but keep a four-hour guest cooldown, return protection and swap protection. Stickiness 10, shared storage, migration domains, current CPU capacity and target RAM reserves still apply. Save settings before starting a run.

    Advanced: thresholds, timing, migration traffic and maintenance
    Overload response and migration limits

    Thresholds require sustained measurements with a five-point recovery margin. Confirmed critical CPU or memory stalls can trigger earlier relief. CPU relief separates heavy consumers; memory relief prefers idle guests. Backup activity pauses every new migration, including Run now and maintenance.

    Each migration adds up to 100 penalty points, decaying once per elapsed minute. Cooldowns and return protection still apply. The hourly limit applies only to continuous balancing; confirmed critical pressure can bypass it. Backup checks cannot be bypassed.

    Migration traffic

    0 uses the Proxmox datacenter migration bandwidth setting. Applies to every migration ProxHA submits, including manual migrations.

    0 means no extra limit beyond each queue's parallel limit. When set, maintenance evacuation sends further guests to other hosts or waits, and together-group repairs use at most this many parallel migrations.

    Maintenance evacuation

    Default: 3. Keep up to this many maintenance migrations running while capacity permits. Changes apply to active evacuations; reducing the limit lets submitted migrations finish. Unrelated DRS migrations remain one at a time; together-groups use their own parallel limit.

    Observed demand uses the last five minutes of guest memory usage plus 20% and 256 MiB per guest, with 2 GiB reserved for the host. This allows configured RAM to exceed physical capacity during evacuation. Target ranking also considers resident memory and CPU. Strict mode reserves configured RAM. Normal DRS keeps its existing limits.

    N+1 capacity monitoring

    Checks each available host failure in the background, even with the browser closed. Results remain available in DRS Overview. This is a failover reserve estimate, not a current load alarm. Configured RAM can exceed physical RAM in an overcommitted cluster. Checks never migrate guests, enable HA or reserve resources. Status changes are retained for seven days.

    Physical I/O and network sources

    Optional Prometheus node_exporter. Polls every 15 seconds, keeps raw data for 24 hours and minute means/peaks for seven days. Select physical disks and interfaces to avoid counting bridges, bonds and their members twice. Interface drops/errors are not end-to-end packet loss.

    Relative CPU performance per host

    Proxmox measures CPU in logical cores. When hosts differ, enter how much work one logical core does compared with a reference host (1). A guest using two cores on a host rated 2 needs four cores on a host rated 1. Hosts with SMT can be rated below 1 when sibling threads share a core. Allowed range: 0.25 to 4.

    Replay recorded data

    Runs the planner over recorded observations every five minutes. Suggestions are not applied between steps. Continuous mode uses its saved aggressiveness; use the comparison below for one-minute persistence checks.

    Only administrators can run replays.

    Compare continuous aggressiveness

    Compare levels against the same recorded data. The saved level is always included as the reference. This does not change settings or migrate guests. Results measure suggestions and planner gates, not the number of migrations that would have completed.

    Aggressiveness levels

    Only administrators can run comparisons.

    Notifications

    ProxHA posts JSON with event, title, message, text and created_at to the webhook. Chat webhooks that read text, such as Slack or Mattermost, show the message directly. Failed deliveries are retried for 24 hours. The saved URL is encrypted and only its host is shown.

    Events

      Scheduled balancing seeks a feasible distribution within migration domains, disk restrictions, stickiness and capacity limits; equal host utilization is not guaranteed. Each schedule starts one queue, with parallel migrations within together-groups, with no fixed migration count limit. Failed guests are skipped for that run. Backup detection cancels the run until the next schedule; submitted migrations finish normally. Starts missed by more than 15 minutes are skipped. Evaluate now is a preview and does not consume a scheduled run. Each move requires fresh validation.
